# TRACK requirements

Requirement text is taken from SPEC.md, spec-addendum-2026-11-06.md, spec-addendum-2026-11-12.md.

- TRACK-001: `SPEC_STATUS.md` MUST list every specification ID exactly once, with status and verification evidence.
- TRACK-002: Maintain a lightweight automated check ensuring every specification ID exists exactly once in the status register.
- TRACK-003: `WORKLOG.md` MUST be append-oriented and concise. Each completed work unit records:
- TRACK-004: `DECISIONS.md` records only consequential architecture decisions, their rationale and consequences. Do not duplicate existing architecture documentation.
- TRACK-005: Update tracking files at meaningful work-unit boundaries, not after every edit. Batch related spec updates.
- TRACK-006: On context reset or resumed execution, read the tracking files and repository status first. Continue from the recorded next action without repeating completed reconnaissance.
- TRACK-007: The work log MUST remain compact. Preserve actionable history and verification evidence, but avoid growing narrative summaries.
- TRACK-008: The final completion report MUST derive from the verified specification register.
- TRACK-009: ID format. The register check accepts IDs of the form `PREFIX-NNN` and `PREFIX-SUBPREFIX-NNN`, where each prefix is upper-case letters and digits starting with a letter (regular expression `[A-Z][A-Z0-9]*(?:-[A-Z][A-Z0-9]*)?-\d{3}`). Today the check's pre-filter `^\| [A-Z]+-\d` silently skips rows such as `SEC2-001`; after this change a row that looks like an ID but does not match is a test failure, not skipped.
- TRACK-010: Every group is declared. `SPEC_GROUPS` lists every prefix used in the register with its highest number, including the groups below. Unknown, missing and duplicate IDs fail the check, as today.
- TRACK-011: No private deployment details in the register. Evidence names no private host names, real LAN addresses, user names or serial numbers. Use the neutral example name `llm-coordinator` and placeholders such as `<Pi LAN address>`. A test fails if the register or `docs/distributed/*.md` contains an RFC 1918 address outside documented example ranges (`<pi-address>` is the example already used in `install.md`; keep a short allow-list) .
- TRACK-012: Final report. `FINAL_REPORT.md` counts are regenerated from the register, including the new groups.
- TRACK-013: Status vocabulary. The row pattern accepts `[w]` and `[d]`. A `[w]` row must cite a decision (`D<number>`). A `[d]` row must cite a decision and a target release (`target 1.6.0`). `FINAL_REPORT.md` counts all six statuses. A script `scripts/spec_open.py` prints, per release, the IDs that are not `[x]`, `[w]` or `[d]`, and exits non-zero when any exist; `--release 1.5.0` treats `[d]` rows targeted at a later release as closed.
- TRACK-014: Test pointers. A row that is `[x]` and is not in the frozen list `tests/spec_legacy_verified.txt` must end with `Tests: <pointer>[, <pointer>...]` or `Evidence: <repository path>`. A pointer is `path::name` for pytest, `path::fn_name` for Rust, or `path::"title"` for Playwright. The check fails when the file does not exist or does not contain the name. The frozen list is created once from the rows that are `[x]` on the day of the change and may only shrink; a test fails when a line is added.
- TRACK-015: Requirement text in the repository. `docs/distributed/spec/` holds one file per ID family with one line of requirement text per ID, imported from the out-of-tree prompts and addenda and cleaned of private deployment details (`TRACK-011`). The check fails when a register ID has no requirement line or a requirement line has no register row. Register rows then hold status and evidence only.
- TRACK-016: Findings are closed by the register. Every finding ID in `docs/distributed/ux-review-web.md` (`WUX`), `review-internals.md` (`INT`), `ux-review-cli.md` (`CLIUX`), `review-findings.md` and `capacity-plan.md` (`F1` to `F10`) appears in a disposition table in its own document with one of: fixed (commit and test), no change (reason), or a register ID. The check parses the tables and fails on a finding without a disposition.
- TRACK-017: Decision numbers. `DECISIONS.md` headings `D<number>` are unique and every `D<number>` cited in the register exists. The check fails on a duplicate or a dangling citation.
- TRACK-018: Release-candidate evidence. `FINAL_REPORT.md` names one CI run on the release-candidate commit that covers all jobs. Rows in the frozen list of `TRACK-014` are covered by that run instead of the run on `c81ccde` of 2026-11-05. The check fails when the named commit is not an ancestor of the tagged commit (checked in the release workflow, not in the unit test).
