# PK requirements

Requirement text is taken from distributed-llm-bridge-followup-prompt.md.

- PK-001: The one recommended passkey path: Tailscale. Keep it simple: one documented path, nothing else.
- PK-002: Canonical origin when passkeys are on. With passkeys, the configuration holds a single `public_origin` (scheme, host, port), from which the RP ID is derived; it is fixed once the first passkey is registered.
- PK-003: Server implementation. Use a maintained WebAuthn library, for example `webauthn-rs` with its passkey APIs, and record the choice in `DECISIONS.md`. Settings. discoverable credentials (resident keys) with `userVerification: "required"`; attestation `none`; ES256 and Ed25519 public-key algorithms, with RS256 accepted for compatibility. Challenges are single-use, at least 128 bits, bound to the session or the setup token, and expire within 5 minutes.
- PK-004: Sign-in user experience. Where passkeys are available, the sign-in page offers them first, with conditional mediation (passkey autofill in the username field, `autocomplete="username webauthn"`) and a "Sign in with a passkey" button that works without typing a username. Passkey sign-in alone counts as multi-factor (possession plus user verification), so no password is asked for. The password stays available as a fallback until the operator turns password sign-in off.
- PK-005: First run. The default first run stays short: open the console, enter the setup token, choose a username and password, save the recovery codes. When the origin supports passkeys, the flow offers "Create a passkey" instead of the password, using Android's own passkey sheet; the password is then optional. Test both variants on an Android-size screen with no documentation.
- PK-006: Passkey management. In settings, the administrator can list, rename and remove passkeys, with the provider's name (from the AAGUID) and whether the passkey is synced. They can add another passkey, including from another device through the cross-device flow. Removing the last sign-in method is blocked. Adding or removing a passkey requires step-up (SEC2-008) and is written to the security log and notifications (SEC2-013 and SEC2-014).
- PK-007: Recovery. Ten single-use recovery codes are shown once and stored as Argon2id hashes. `bridge-coordinator admin reset-passkeys` (local shell only, like `reset-password`) removes all passkeys and sessions and prints a one-time enrolment token, so a lost phone never locks the operator out permanently. Every recovery path is audited.
- PK-008: Step-up with passkeys. Sensitive actions (SEC2-008) accept a fresh passkey assertion as step-up.
- PK-009: API tokens and passkeys. API tokens remain the credential for scripts. Creating a token requires a passkey step-up, so a stolen password alone cannot mint one.
- PK-010: Browser capability detection. The console uses `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` and `getClientCapabilities()` where available. When passkeys are unavailable, settings show one calm sentence saying why (for example "Passkeys need a trusted address such as Tailscale") and a link to "Enable passkeys (optional)". No error, no warning banner, and nothing on the sign-in page.
- PK-011: Automated tests. The Rust unit tests verify the WebAuthn ceremony with fixed vectors. Playwright end-to-end tests drive Chromium's virtual authenticator (CDP `WebAuthn.addVirtualAuthenticator`, internal transport, resident keys, user verification) through every flow: registration, conditional-UI sign-in, button sign-in, step-up, multiple passkeys, removal, and recovery codes. Run the flows at Pixel 4 size, and in Firefox where its virtual authenticator support allows.
- PK-012: Real-device check. The physical verification on a stock Android phone is part of the Pi prompt (VERIFY-013). This branch documents the procedure in `install.md` ("Enable passkeys (optional)") and must not claim Android support beyond the virtual authenticator until that check passes.
