# SEC2 requirements

Requirement text is taken from distributed-llm-bridge-followup-prompt.md.

- SEC2-001: TLS policy. Make TLS 1.3 the default minimum, and make TLS 1.2 (ECDHE with AEAD only) an explicit `min_tls = "1.2"` opt-in for old clients. The server key is ECDSA P-256 or Ed25519 where browsers allow it. Disable TLS session resumption tickets, or rotate their keys at least daily. 0-RTT is off. A CI check, for example `testssl.sh` against the test coordinator, shows no finding of medium severity or above.
- SEC2-002: Response headers on every response, including errors and static files. Keep the existing headers. Add. `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`; a `Permissions-Policy` that turns off every unused feature; for the web console, `Cross-Origin-Embedder-Policy: require-corp`, if xterm.js and the bundle allow it.
- SEC2-003: Strict request handling. Mutations require `Content-Type: application/json`; anything else gets 415. Unknown JSON fields are rejected (`deny_unknown_fields` on every request type, which also protects against mass assignment). JSON nesting depth and every string and array length are bounded, and declared in the OpenAPI schema. Non-ASCII control characters in identifiers are rejected. `HEAD`/`OPTIONS` behaviour and method-not-allowed responses (405 with `Allow`) are explicit.
- SEC2-004: Fetch Metadata resource isolation. For cookie-authenticated requests, reject cross-site requests by checking `Sec-Fetch-Site`, `Sec-Fetch-Mode` and `Sec-Fetch-Dest`. Exempt only top-level navigations to the console's HTML pages. This adds to the CSRF token and the `Origin` check; it does not replace them. Bearer-token requests are unaffected.
- SEC2-005: No CORS by default. If a future configuration allows origins, it takes an explicit list of HTTPS origins, never `*` with credentials, and never reflects the request's `Origin`. A test covers preflight rejection.
- SEC2-006: Simple sign-in by default, passkeys when the address supports them. Anyone must be able to run the coordinator with no domain, no account with any outside service and no extra app. The default sign-in is therefore a password (SEC2-007) with an optional authenticator-app code (TOTP) and one-time recovery codes, stored as hashes. Passkeys are an upgrade that switches on by itself when the console is served on an address that supports them; they are never required and never block setup.
- SEC2-007: Passwords (NIST 800-63B rev. 4). A minimum of 15 characters when the password is the only factor, or 12 with a second factor. No composition rules. Check against a bundled list of common and breached passwords (offline, size-bounded). Allow long passphrases. Keep the Argon2id parameters configurable, with the measured cost on the Pi recorded in `benchmarks.md`.
- SEC2-008: Session hardening. Issue a new session identifier on login and on every privilege change. Bind each session to its own CSRF secret. Show active sessions in the console, with the option to revoke each one. Require a fresh credential for sensitive actions (step-up, valid for 10 minutes): creating or revoking tokens, adding or removing workers, changing a password, restore, and the worker opt-in operations from API-016.
- SEC2-009: API token format and lifecycle. Tokens are prefixed and identifiable (for example `lbr_pat_<id>_<secret>`) so secret scanners can detect them; GitHub secret scanning supports custom patterns. Secrets have at least 256 bits of entropy and are compared in constant time. Every token has an expiry, with a configurable maximum lifetime; tokens that never expire are not allowed in Internet mode. The console shows the last use (time and address).
- SEC2-010: Abuse controls. Rate limits per address and per token on authentication, token use and mutations (`429` with `Retry-After`). Exponential back-off and an alert after repeated failures. A global cap that protects the Pi.
- SEC2-011: Authorisation by design. Every route declares its principal type (browser session, API token or worker token), its scope (API-005) and its object rule (which workers and missions it may reach). A central policy layer enforces these declarations, and a router-enumeration test fails on any route without one. Worker tokens can never reach browser or API routes, and browser or API credentials can never reach worker routes. Test both.
- SEC2-012: Least data. Responses contain only fields the schema declares, with serialisation driven by the schema. Never return internal paths outside mission folders, environment variables, provider credentials, token hashes or stack traces. 5xx responses are generic `problem+json` with a correlation ID that also appears in the server log. List endpoints cap their page size.
- SEC2-013: Security event log. Log authentication successes and failures, token creation, use and revocation, step-up, configuration changes, worker opt-in operations and authorisation denials. Each entry records the principal, token name and ID, address, user agent, request ID and outcome, never a secret. Entries form a hash chain so tampering is detectable, are retained within the storage bounds, and can be read through `GET /api/v1/audit` (`admin` scope) and the console.
- SEC2-014: Notifications. The console shows a security banner after a sign-in from a new address or device, after a token is created, and after repeated failures. An optional webhook notifies the administrator of the same events, as an outbound HTTPS POST to a configured URL with no secrets in the payload.
- SEC2-015: Supply chain. Pin GitHub Actions to full commit SHAs, with Dependabot updates; today they are pinned by tag. Run `cargo audit` and `cargo deny` (advisories, licences, duplicate and unknown sources), `npm audit --omit=dev` for the web bundle, and `pip-audit` for the Python dev dependencies in CI. Produce a CycloneDX SBOM for the container image. Sign the image and attach provenance (cosign or GitHub artifact attestations). Document how to verify the signature in `install.md`.
- SEC2-016: Dynamic security testing in CI. Run an OWASP ZAP API scan, driven by the OpenAPI document, against a test coordinator, and a ZAP baseline scan of the console. Together with the Schemathesis fuzzing from API-012, these must find nothing of medium severity or above, or each finding is accepted in `review-findings.md` with a reason. Add negative tests for every SEC2 requirement.
- SEC2-017: Separate listeners and trusted proxies. Split routes into three groups: the console and REST API, the worker channel (`/api/v1/worker/*`) and health. Each group can be bound to its own listener (address and port), so an operator can expose only one group. A `trusted_proxies` list (CIDR) is the only source of client addresses from `Forwarded` / `X-Forwarded-For`; without it, these headers are ignored. The coordinator works unchanged behind a TLS-terminating reverse proxy or a zero-trust tunnel.
- SEC2-018: An `exposure` setting. It takes `loopback` (default), `lan` or `internet`; replace `lan_enabled` with it and migrate the old setting.
- SEC2-019: Pluggable components. Put certificate provisioning behind an interface with three implementations planned: the internal CA (today), files supplied by the operator, and ACME (leave a documented stub only; not implemented in this branch). Put authentication behind an `Authenticator` interface: password, passkey and TOTP now; OIDC later. Store sessions, tokens and audit entries against a principal ID, not "the administrator", so more users and roles can be added later without a schema rewrite.
- SEC2-020: Worker channel for the Internet. Workers already connect outbound with a pinned CA and per-worker tokens. Add optional mutual-TLS worker authentication (client certificates issued by the coordinator CA during enrolment) and worker token rotation without re-enrolment. Keep the worker-enforced opt-ins from API-016, so a compromised coordinator stays limited to the operations each worker allows.
