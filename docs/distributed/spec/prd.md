# PRD requirements

Requirement text is taken from distributed-llm-bridge-release-prompt.md; IDs marked (source text not found) have no text in these sources and are summarised from their register row.

- PRD-001: Five-minute first success. A new user with only the README goes from nothing to a coordinator, one enrolled worker and a running mission visible live in the browser in at most 5 minutes on Linux (container), macOS and Windows. Measure it with a scripted walkthrough per platform (the steps a user types, timed) and fix every step that needs knowledge the page does not give. The console's first run guides worker enrolment with copyable, pre-filled commands (worker token shown once).
- PRD-002: Release artifacts. Each release publishes: the multi-architecture coordinator image (amd64, arm64) to a registry, signed with provenance and an SBOM (SEC2-015); the Python package; and checksums. `release.yml` builds them from a tag; a dry-run job proves it on every PR.
- PRD-003: Versioned upgrades and migrations. Every coordinator and worker database migration is forward-only, tested from each of the last released schema versions with a fixture database, and runs automatically at start with a backup taken first. A downgrade refuses with a clear message naming the backup. Protocol version negotiation between a worker one minor version older or newer and the coordinator is tested in CI (old worker, new coordinator and the reverse).
- PRD-004: Configuration validation. `bridge-coordinator check-config` and the start-up path report every configuration error at once with the key, the value and the fix; unknown keys are errors with a "did you mean". Tested table-driven.
- PRD-005: Uninstall and data portability. Documented and tested uninstall for each install method that leaves no service, port or file behind except what the user chose to keep; `backup` output restores on another host and another architecture.
- PRD-006: Documentation as product. A user guide (concepts, the five tasks every operator does, troubleshooting by symptom) on the site, every error message in the product linking to its troubleshooting entry, and a docs check in CI that every error code has an entry and every CLI command and REST endpoint is documented.
- PRD-007: Soak test. A 24-hour CI-runnable soak (scaled down to 30 minutes in PR CI, full length nightly) with one coordinator, 10 workers and 50 missions driven by fake providers producing output, questions, rate limits and crashes. Pass criteria: no lost or duplicated command, no unbounded memory, file-descriptor, task or database growth (sampled every minute, slope within a stated bound), p99 API latency within budget.
- PRD-008: Chaos. Automated fault injection: coordinator restart and kill -9 during command delivery, worker network partition and reconnect with replay, disk full on the coordinator data volume, clock jump forwards and backwards, slow and dropped WebSocket frames, a corrupt database page. Each fault has an expected outcome (no silent loss, uncertain outcomes reported as uncertain, recovery without a person) and a test.
- PRD-009: Capacity limits. Measured and documented limits per coordinator (workers, missions, events per second, concurrent browser sessions, concurrent terminal viewers) on x86-64 and on the Pi Zero 2 W, with graceful degradation and clear errors when exceeded (no crash, no unbounded queue). Tested at the limit.
- PRD-010: Data retention. Events, audit entries, operations and terminal scrollback have documented, configurable retention with defaults that keep a Pi's card within its budget for a year of continuous use (computed from the PRD-007 growth figures), enforced by background pruning with audit records.
- PRD-011: Observability for the operator. A `/metrics`-style health page in the console and `bridge-coordinator diagnostics` output (no telemetry, nothing leaves the host): uptime, versions, connected workers, command queue depth, event lag per worker, database size and growth, last backup age, certificate expiry, update availability check opt-in only. Each value has a threshold that turns it into a console warning with the fix.
- PRD-012: Diagnostic bundle. `bridge-coordinator support-bundle` and `llm-bridge doctor --bundle` produce a redacted archive (configuration without secrets, versions, recent logs with tokens and prompts removed, health) for bug reports; a test proves seeded secrets, tokens, prompt text and private addresses are absent.
- PRD-013: Backups by default. Scheduled automatic coordinator backups with rotation are on by default, their age is shown in the console, and restore is a guided console action for the administrator (step-up required, SEC2-008).
- PRD-014: Mission control at a glance. The overview answers in one screen, for any number of workers and missions: what needs me now, what is running and what is it doing (live provider line), what failed, what is rate-limited and until when, which worker is unhealthy. Sorting and grouping keep the attention items first. Virtualised lists stay smooth at 500 missions.
- PRD-015: Live session view. For each running mission: the live provider output (UX-007), the current prompt and task, the provider and model, token or capacity use where known, elapsed time, the last tool call, and the history of turns, with search within the scrollback and copy. Works at Pixel 4 size.
- PRD-016: Full operator control from the console. Every operator action the CLI offers (API parity table, PAR-001 to PAR-014) is reachable in the console with the same vocabulary: create mission (when the worker allows it), start, pause, resume, stop, finish, steer every kind, add and amend tasks, priority and dependencies, approve with evidence and reject with a reason, answer a provider's question (DOG-010), rotation and settings. Destructive actions confirm and are undoable where the model allows.
- PRD-017: Command palette and keyboard. Cmd/Ctrl-K reaches every page, mission, worker and action; every action has a keyboard path; shortcuts are discoverable and documented in the console.
- PRD-018: Notifications. Optional browser notifications (with permission) and an in-console inbox for: needs you, task waiting for verification, mission failed, worker offline for more than N minutes, rate limit lifted; each links to the place to act. Optional webhook (SEC2-014).
- PRD-019: Accessibility. WCAG 2.2 AA throughout: axe-core zero violations on every page and state, full keyboard operation, screen-reader-tested flows (NVDA or Orca script) for sign-in, approve, reject and terminal view, contrast in both themes, focus management on every route change.
- PRD-020: Performance budgets. First load under 1.5 s on a mid-range phone over Wi-Fi from a Pi Zero 2 W coordinator, route changes under 100 ms, INP under 200 ms and CLS under 0.05 at Pixel 4 with 4x CPU throttling, the bundle budget enforced in CI; measured against the Pi.
- PRD-021: Browser matrix. Current and previous major versions of Chrome, Edge, Firefox and Safari (desktop and iOS), and Chrome on Android, in CI where Playwright supports them; any unsupported browser gets a clear message.
- PRD-022: Internationalisation-ready. All user-visible strings in one catalogue, dates and numbers locale-formatted, layout tested with 30 percent longer strings; English only at release.
- PRD-023: External-style penetration test. A structured test against the release candidate following the OWASP WSTG and API Top 10, by an independent reviewer agent briefed only with the code and docs, with every finding fixed or accepted with a reason; repeat ZAP, testssl.sh and Schemathesis on the candidate.
- PRD-024: Security policy. `SECURITY.md` with a reporting address and process, supported versions, and an advisory process; GitHub private vulnerability reporting enabled (document the setting; enabling it is the owner's action).
- PRD-025: Dependency hygiene. Dependabot for Cargo, npm, Actions and pip-dev; a weekly scheduled audit job; a documented policy for responding to advisories within a stated time.
- PRD-026: Safe defaults review. Every setting reviewed for its default: loopback binding, no CORS, token expiry, session lifetimes, rate limits, worker opt-ins off, backups on. A test asserts each default.
- PRD-027: Abuse resistance at scale. Brute force, token stuffing, WebSocket flooding and oversized payload attempts against a Pi-sized coordinator stay within the documented limits without degrading other users' sessions (tested).
- PRD-028: Release candidate checklist. A `docs/distributed/RELEASE_CHECKLIST.md` that the release workflow enforces: register fully `[x]`, all gates green, soak and chaos green on the candidate, migration tests green, artifacts signed, docs and changelog updated.
- PRD-029: Changelog and versioning. Semantic versioning for the coordinator, worker protocol and REST API (additive within `v1`), a user-facing changelog per release written for operators, and deprecation notices surfaced in the console.
- PRD-030: Release candidate dry run. Cut a release candidate tag on the branch (pre-release, not `latest`), install it fresh and upgrade the Pi coordinator to it through the documented path, run PRD-001's walkthrough on it, and record the results. The final non-candidate release tag is the owner's decision; report readiness and wait.
- PRD-031: Expert UX review of the CLI and terminal console. An independent reviewer briefed as a principal UX designer for developer tools reviews every `llm-bridge` command (help text, argument names, defaults, output layout, `--json`, error messages, exit codes, first run, `doctor`), the home screen, the console views F1 to F8, overlays, the composer and the tmux station, at 80x24 and 140x40, UTF-8 and ASCII, dark and light.
- PRD-032: Expert UX review of the web console and site. The same reviewer brief for every page and state of the web console and the Pages site at 1440x900 and Pixel 4, both themes, keyboard only and with a screen reader. Findings in `docs/distributed/ux-review-web.md`. Builds on UX-001 to UX-011; it repeats the review on the merged product rather than trusting the earlier audit.
- PRD-033: Every UX finding fixed. Every finding of PRD-031 and PRD-032, of every severity, is fixed with a test (golden screen, Playwright baseline or assertion) that fails before the fix. Nothing is accepted as "won't fix" without the operator's written agreement in the register. A second reviewer pass on the fixed product finds no new high or medium issue.
- PRD-034: Review of the inner workings. An independent architecture and correctness review of the controller, store, runtime, worker, protocol, coordinator and web client: state machines and their invariants, concurrency and locking, idempotency and replay, error handling and uncertain outcomes, resource bounds, recovery after every crash point, and code that is duplicated or dead.
- PRD-035: No open issues. At release: every dog-food finding (DOG-*, including the low ones), every review finding (REV-*, PRD-031 to PRD-034), and every open GitHub issue on the repository labelled for Bridge is fixed and closed; flaky tests are root-caused, not retried (the CI history of the last 50 runs on `main` has no unexplained failure).
- PRD-036: Password reset over SSH. A locked-out operator resets the web console password from an SSH session on the coordinator host with one documented command, on container, native and Pi installs; interactive prompt, `--temporary` with a forced change at the next sign-in, documentation and login-page help (operator request of 2026-11-07; details in mission task 5).
- PRD-037: (source text not found) Web console redesign as a release blocker: the live provider session is the primary pane of the mission page, with a sticky steer composer and always-visible Pause and Stop.
- PRD-038: (source text not found) `llm-bridge mission delete ID` is available from the CLI, the web console and the REST API, and deletes only CREATED, COMPLETED, FAILED, CANCELLED or STOPPED missions.
