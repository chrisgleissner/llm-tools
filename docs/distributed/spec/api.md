# API requirements

Requirement text is taken from distributed-llm-bridge-followup-prompt.md.

- API-001: Add resource-oriented endpoints under `/api/v1` for the objects the console shows. `workers`, `missions`, `missions/{id}/tasks`, `missions/{id}/events`, `missions/{id}/operations`, `commands/{request_id}` and `diagnostics`;
- API-002: Each endpoint is a thin adapter over the existing typed command layer (`llm_tools/bridge_commands.py` on the worker and the coordinator's command routing). Do not add a second implementation of any state transition (QUAL-001). `POST /commands` stays as the low-level endpoint, and the web console and `llm-bridge remote` move to the resource endpoints.
- API-003: Mutations follow the existing durable-command model. the `Idempotency-Key` header maps to the request ID, so a repeat returns the stored outcome; `ETag` and `If-Match` map to `expected_revision`, and a stale revision gives 412; a mutation for an offline worker returns 202 with a `Location` of `commands/{request_id}`; an uncertain outcome is reported as uncertain, never as success.
- API-004: Errors use `application/problem+json` (RFC 9457), with a stable `type` URI per error code that reuses the existing error codes. List endpoints use opaque cursor pagination (`cursor`, `limit` with a documented maximum) and stable sorting. Timestamps are RFC 3339 in UTC.
- API-005: API tokens get scopes. `read` (all GET); `operate` (mission and task actions); `terminal:view` and `terminal:write`; `admin` (workers, tokens, diagnostics).
- API-006: The administrator manages tokens through the API (`GET/POST/DELETE /api/v1/tokens`, with name, scopes, expiry and last use; the secret is shown once at creation). Token management requires a browser session plus CSRF, or a token with `admin` scope. Add it to the web console.
- API-007: Keep every existing protection. TLS only, the coordinator CA and loopback publishing by default; CSRF and exact `Origin` for cookie sessions, while bearer tokens are exempt from CSRF and never accepted from query strings; the body size limits; no CORS headers by default, with an explicit allow-list setting if ever needed.
- API-008: Never return secrets, provider credentials, environment variables or raw terminal content through REST. Terminal access stays on the WebSocket and requires the terminal scopes.
- API-009: Generate an OpenAPI 3.1 document from the Rust types and route declarations, for example with `utoipa` and its axum integration. Choose the crate and record the decision in `DECISIONS.md`. Serve it at `GET /api/v1/openapi.json`; it is public and contains no secrets or instance data. Include schemas, examples, error responses, scopes, pagination, `Idempotency-Key` and `If-Match`.
- API-010: Serve a human-readable API reference page from the coordinator itself, at `/api/docs` or in the web console. Its assets are bundled locally under the existing Content Security Policy: no CDN and no inline script that the policy forbids. Count it in the bundle budget. If a self-hosted renderer would break the budget, render a static HTML reference from the document at build time instead.
- API-011: Commit a generated snapshot (`docs/distributed/openapi.json`). CI regenerates the document and fails when it differs from the snapshot, which forces API changes to be reviewed. A second check fails on a breaking change against the last released snapshot (a removed path, operation or field, or a newly required field) unless the version changes.
- API-012: Contract tests. every response in the Rust API tests and in the Python integration tests is validated against the generated schema; the deliberately failing requests return the documented problem types; the scope matrix is tested for every route: each scope gets 401, 403 or success as declared.
- API-013: Switch `llm-bridge remote` and `--target` to the resource endpoints, using a small standard-library client whose request and response types are generated from or checked against the OpenAPI document. Its CLI behaviour, exit codes and `--json` output stay unchanged.
- API-014: Documentation. an "API" section in `coordinator.md`, with authentication, scopes, idempotency, concurrency, pagination, errors, rate limits and versioning (additive changes within `v1`, breaking changes only in `v2`, and a deprecation header policy); a short `docs/distributed/api.md` with `curl` examples for the main tasks (list missions waiting for approval, approve one, add a task); a link from the README and the site.
- API-015: Every CLI command and option is either mapped to an operation and endpoint, or listed as excluded with a reason, in a parity table in `docs/distributed/api.md`. A test builds the CLI's argparse tree (`bridge._build_parser`) and the coordinator's route table and fails when any command or option lacks a mapping or an exclusion, or when a mapping names a missing route. A new CLI command therefore cannot be added without a REST decision.
- API-016: The new worker opt-ins (`--allow-create` with `--allow-root`, `--allow-power` and `--allow-restore`) are off by default, shown in `worker status` and in `GET /workers/{w}`, and enforced by the worker, not only by the coordinator. A test checks that the coordinator cannot bypass them, even with an `admin` token. The new operations are also available through `llm-bridge --target WORKER`, under the same rules.
