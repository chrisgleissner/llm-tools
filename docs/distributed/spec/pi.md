# PI requirements

Requirement text is taken from distributed-llm-bridge-pi-setup-prompt.md.

- PI-BOOT-001: Ask the user to move the card into the Pi and connect the Pi's data USB port to the desktop (it powers the Pi). Explain that the Broadcom `0a5c:2764` USB boot device only shows the boot ROM, not Linux.
- PI-BOOT-002: Find the Pi on the LAN without guessing: try `llm-coordinator.local` (mDNS), the router's DHCP lease list (ask the user), or a bounded scan of the local /24 for SSH. Connect with `ssh root@<ip>` and the key.
- PI-BOOT-003: Wait for first-run setup to finish: `/boot/dietpi/.install_stage` must read `2`. First-run setup runs `apt upgrade` and reboots. Known DietPi behaviour seen in the rehearsal: if first-run setup fails, DietPi deliberately sets `AUTO_SETUP_AUTOMATED=0` and leaves `/tmp/.dietpi-login_firstrun_setup.pid`; diagnose the failure first, then restore the flag, remove a pid file whose process no longer exists, and rerun `/boot/dietpi/dietpi-login` in a pseudo-terminal (`script -qfec`).
- PI-BOOT-004: Verify: `uname -m` = `aarch64`, `dpkg --print-architecture` = `arm64`, `/etc/os-release` = Debian 13 (trixie), hostname `llm-coordinator`, model `Raspberry Pi Zero 2 W` (`cat /proc/device-tree/model`), 4 CPUs, RAM, card size.
- PI-BOOT-005: The rehearsal's DietPi MOTD reported a pending kernel upgrade for CVE-2026-98432. Run `apt update && apt full-upgrade`, reboot, and confirm the running kernel (`uname -r`) is the installed one and the MOTD warning is gone.
- PI-DEPLOY-000: Docker address ranges: Before starting any container, compare Docker's default ranges (default bridge <pi-address>/16, then further networks from <pi-address>/16 upward) with the home LAN (`ip -4 route` on the Pi and on the Ubuntu host) and any VPN. If anything overlaps, add `"bip": "<pi-address>/24"` and `"default-address-pools": [{"base": "<pi-address>/16", "size": 24}]` (or other free ranges) to `/etc/docker/daemon.json`, keeping the existing keys, and restart Docker.
- PI-DEPLOY-001: On the Ubuntu host: build the arm64 image with `container/build.sh --oci <archive>` (cross-compiled; nothing builds on the Pi). Copy the archive with `scp` and load it on the Pi (`docker load`, or `skopeo` as the guide describes). Copy `container/compose.yaml` to `/opt/llm-bridge/` on the Pi.
- PI-DEPLOY-002: Create `.env` with `BRIDGE_PUBLISH_ADDRESS=<Pi LAN address>` and `BRIDGE_PUBLIC_NAMES=llm-coordinator.home.arpa,llm-coordinator.local,<Pi LAN address>` (only names that actually resolve), then `docker compose run --rm coordinator init` and `docker compose up -d`.
- PI-DEPLOY-003: Open the coordinator port in the firewall for the LAN subnet only (HARD-003 rollback procedure again).
- PI-DEPLOY-004: Copy `ca.pem` and the setup token to the desktop. Import the CA into Chrome and Firefox following `install.md` ("Trusting the certificate"), checking the SHA-256 fingerprint from `bridge-coordinator info`. No certificate warning may be bypassed.
- PI-DEPLOY-005: Create the administrator through the browser with the setup token. The administrator password is chosen by the user or generated into `secrets/`; never printed.
- PI-DEPLOY-006: On the desktop: enrol it as a worker (`bridge-coordinator worker add`, then `llm-bridge worker enroll` and `llm-bridge worker run` as the guide describes), create an API token and `llm-bridge remote login`. Verify `llm-bridge worker list`, `llm-bridge --target <worker> status`, `llm-bridge --target all mission list`, a remote task add or approval, and the live event stream and terminal in the browser.
- PI-DEPLOY-007: Open the web UI from an Android phone on the same Wi-Fi (Chrome and Firefox), after importing the CA on the phone as `install.md` describes. Check login, overview, missions and the terminal view in portrait and landscape.
- PI-FLASH-001: Confirm the image in `dl/` still matches its `.sha256` (`sha256sum -c`).
- PI-FLASH-002: Verify the PGP signature. The signing key is RSA `C2C4D1DEF7C96C6EDF3937B2536B2A4A2E72D870`. Obtain the public key from a DietPi-published source (for example the DietPi GitHub repository or keys.openpgp.org) and confirm the fingerprint from a second, independent DietPi source before trusting it. Import into a temporary `GNUPGHOME`, never the user's keyring. If no second source exists, record that and continue on the strength of the SHA-256 match from the official site.
- PI-FLASH-003: Decompress to `dietpi.img` and edit the FAT boot partition without root using `mtools` (`mcopy -i dietpi.img@@<offset>`; the offset is the first partition's start sector times 512, from `sfdisk -d`). The rehearsal verified this method.
- PI-FLASH-004: In `dietpi.txt`, set (all keys verified to exist in this image; see the research file).
- PI-FLASH-005: Ask the user for the 2.4 GHz SSID and passphrase. Write them only into `dietpi-wifi.txt` as `aWIFI_SSID[0]` and `aWIFI_KEY[0]` (`aWIFI_KEYMGR[0]='WPA-PSK'` is the template default). Do not echo them. Confirm by reading the keys back and printing only whether they are non-empty.
- PI-FLASH-006: In `config.txt`, set the minimum GPU memory split for headless use if this DietPi release does not already (check `gpu_mem` and DietPi's documented setting; do not add unsupported keys).
- PI-FLASH-007: Optional USB fallback for first contact: the Pi is attached to this desktop by its USB data port. If Wi-Fi fails, USB gadget Ethernet (`dtoverlay=dwc2` in `config.txt`, `modules-load=dwc2,g_ether` in `cmdline.txt`) gives a `usb0` link (the image already contains `/etc/network/interfaces.d/usb0.conf`). Prepare this only if the user agrees, and document how to remove it afterwards.
- PI-FLASH-010: Ask the user to insert the SanDisk Extreme 128 GB microSD card (about 126 GB usable) into slot 0 of the Norelsys NS1081 reader. The previous "original" card failed to initialise (0 bytes); do not use it. The 119 GB card may be used only if the user confirms its `bootfs`/`rootfs` contents may be erased.
- PI-FLASH-011: Identify the card (EXEC-003) and show the user model, serial, size and partitions.
- PI-FLASH-012: After explicit approval naming the device, ask the user to run, with the `!` prefix: `! sudo dd if=dietpi.img of=/dev/<approved> bs=4M conv=fsync status=progress && sync`
- PI-FLASH-013: Verify the write: ask the user to run `! sudo cmp -n <image size> dietpi.img /dev/<approved>` (no output means identical), then check `lsblk` shows the two partitions. Then delete `work/dietpi.img`, because its `dietpi.txt` contains the generated password.
- PI-HARD-001: Create a non-root administrative user with the same SSH key and `sudo`. Verify a fresh SSH login as that user and `sudo -v` before disabling remote root login. Record the recovery path (local console on the card, or re-flash).
- PI-HARD-002: Keep Dropbear unless a verified reason favours OpenSSH. Password login stays disabled.
- PI-HARD-003: Firewall with nftables (or DietPi's supported option): default drop inbound; allow SSH and, later, the coordinator port only from the LAN subnet discovered on the device (`ip -br a`, `ip route`). Before applying, schedule an automatic rollback (`systemd-run --on-active=120 nft flush ruleset`, or equivalent) and cancel it only after a fresh SSH login succeeds.
- PI-HARD-004: `ss -lntup` must show only SSH and the DHCP client (and later the coordinator). No other listening services.
- PI-HARD-005: Time synchronisation active and synchronised (`timedatectl`). The Pi has no RTC; TLS and sessions depend on the clock.
- PI-HARD-006: Hostname resolution: `llm-coordinator.home.arpa` if the LAN DNS supports it, otherwise `llm-coordinator.local` via mDNS (Avahi only if DietPi provides it and it is needed), otherwise the IP. Recommend a DHCP reservation on the router; do not change the router without explicit authorisation.
- PI-REPO-001: Update `docs/distributed/benchmarks.md` with a "Raspberry Pi Zero 2 W (physical)" column or section next to the GitHub ARM64 runner and emulated figures, with method and date.
- PI-REPO-002: Update the "Raspberry Pi Zero 2 W target profile" section of `install.md`: replace "not yet measured" and every derived figure with the physical measurements; keep the rest of the documentation hardware-neutral.
- PI-REPO-003: Update the evidence of the affected IDs in `SPEC_STATUS.md` (at least COORD-001, COORD-003, OPS-001, OPS-002, TEST-012, TEST-013, TEST-014, TEST-015) with the physical results, and close the "physical Pi verification" follow-up in `FINAL_REPORT.md`. Regenerate the report's counts from the register.
- PI-REPO-004: Fix any defect found on the device at its root in the repository, with a test that fails before the fix. Never weaken a test or a limit to make the device pass.
- PI-REPO-005: Run the repository's required gates (`python -m pytest -q`, both coverage gates from `AGENTS.md`, `cargo test` in `coordinator/`, the web tests), create a separate worktree ((if `llm-tools-pi` already exists, for example because an overseer created it before starting this run through LLM Bridge, use it as it is) `git -C llm-tools fetch origin && git -C llm-tools worktree add llm-tools-pi -b feat/pi-zero-2w-verification origin/main`;
- PI-REPO-006: Update `pi-zero-2w-research.md`: move every "pending" entry to its physical result.
- PI-SYS-001: Remove or disable demonstrably unnecessary services; keep DietPi's management and recovery tools.
- PI-SYS-002: Docker: data root on the card, default log driver `journald` (section 7b, WEAR-002), live-restore enabled, no experimental features, no Swarm or orchestration layers. Confirm `docker info` and `docker compose version`.
- PI-SYS-003: Swap: zram only, no swap file on the card (section 7b, WEAR-003). The coordinator's container never swaps (`memswap_limit` equals `mem_limit`).
- PI-SYS-004: Logging: system, journal and container logs stay in RAM (section 7b, WEAR-001 and WEAR-002). Never place authoritative state on tmpfs.
- PI-SYS-005: Power: `vcgencmd get_throttled` must be `0x0`; inspect `dmesg` for undervoltage. If the desktop USB port is marginal, recommend a dedicated 5 V 2.5 A supply.
- PI-SYS-006: Fully automatic daily updates: see section 7a. Manual intervention must never be needed for routine updates.
- PI-UPD-001: APT updates through Debian's standard `unattended-upgrades` (installed with `apt-listchanges` absent), not DietPi's cron upgrade.
- PI-UPD-002: Set `CONFIG_CHECK_APT_UPDATES=1` (check only) in `/boot/dietpi.txt`, so DietPi's cron job and `unattended-upgrades` never run APT concurrently. Keep `CONFIG_CHECK_DIETPI_UPDATES=1` for the banner.
- PI-UPD-003: DietPi core updates through a systemd timer: `dietpi-auto-update.service` (`Type=oneshot`, `ExecStart=/boot/dietpi/dietpi-update 1`, `Environment=G_INTERACTIVE=0`, `After=network-online.target time-sync.target`, `Wants=network-online.target`, a generous `TimeoutStartSec`, `Nice=10`, `IOSchedulingClass=idle`) and `dietpi-auto-update.timer` (`OnCalendar=*-*-* 03:30`, `RandomizedDelaySec=20min`, `Persistent=true`, so a missed day runs after the next boot).
- PI-UPD-004: Reboots: `unattended-upgrades` reboots at 04:30 when `/var/run/reboot-required` exists. Raspberry Pi kernel packages may not create that file; add a small `/etc/kernel/postinst.d/zz-reboot-required` hook (or a check in a drop-in) that creates `/var/run/reboot-required` when the newest installed kernel differs from `uname -r`. Verify with a real kernel update, not by assumption.
- PI-UPD-005: Containers: Docker Engine updates arrive through APT. Enable `live-restore` so the coordinator container keeps running while `dockerd` restarts, and keep `restart: unless-stopped`. Container images are not auto-updated from a registry: the coordinator image is built on the desktop and loaded deliberately (section 8). Record this as a decision.
- PI-UPD-006: Transparency: every run logs to the journal (`journalctl -u dietpi-auto-update -u apt-daily-upgrade`) and `/var/log/unattended-upgrades/`. Add a tiny `update-status` command (shell script under `/usr/local/sbin`) that prints the last successful run of each timer, the pending reboot state, the running and newest installed kernel, and the DietPi version. A failed run must be retried automatically on the next day (the timers do this) and be visible in `systemctl --failed`.
- PI-UPD-007: Recovery from interrupted runs: a drop-in `ExecStartPre=/usr/bin/dpkg --configure -a` on `apt-daily-upgrade.service`, so a power cut during an upgrade is repaired by the next run instead of needing a person.
- PI-UPD-008: Exception, stated plainly to the user: Debian major release upgrades (Debian 13 to 14) are not routine updates and are not applied unattended, because a release upgrade can change services and configuration in ways no unattended run can verify. DietPi announces them; plan them as a separate, supervised step. Everything else is unattended.
- PI-UPD-009: Verify end to end on the device: run both services once by hand (`systemctl start dietpi-auto-update.service apt-daily-upgrade.service`) and confirm success; confirm `systemctl list-timers` shows both timers with next run times; simulate a missed run (`systemctl stop` the timer, move the stamp file back, reboot) and confirm `Persistent=true` triggers it;
- PI-VERIFY-001: OS, architecture, kernel, CPU count, RAM, card size and free space (BOOT-004).
- PI-VERIFY-002: SSH key-only administration, firewall rules, listening ports (only SSH, DHCP client and the coordinator on the LAN address).
- PI-VERIFY-003: Hostname, IP, DNS, time synchronisation.
- PI-VERIFY-004: Idle baseline without Docker containers running: `free -m`, `uptime` load, `top -bn1` CPU, and `dockerd` plus `containerd` RSS.
- PI-VERIFY-005: Coordinator: idle RSS, RSS after logins (Argon2id allocates on first use), peak under `deploy/bench.sh`, `docker stats --no-stream`, start time, `/api/v1/diagnostics`, API latency, event throughput, reconnect latency, and database growth per 1,000 events. Use the same method and units as `docs/distributed/benchmarks.md`. Recommend the memory limit from the measured peak (raise `BRIDGE_MEMORY_LIMIT` if the peak exceeds about 80 percent of 96 MiB).
- PI-VERIFY-006: Reboot: `reboot`, then confirm Wi-Fi returns, SSH works, the coordinator container is healthy without manual action, the worker reconnects by itself, and no task ran twice.
- PI-VERIFY-007: Wi-Fi interruption: schedule `systemd-run --on-active=60 ip link set wlan0 up`, then `ip link set wlan0 down`. Confirm the web UI and worker show offline or stale state, then recover by themselves, with no duplicated execution.
- PI-VERIFY-008: Power loss (needs the user): with a write load running, ask the user to unplug the Pi for 10 seconds and plug it back in. Confirm the filesystem and the coordinator database are intact (`bridge-coordinator health`, SQLite `PRAGMA integrity_check` through the coordinator's own tooling) and that the coordinator recovers.
- PI-VERIFY-009: Persistence of `/var/lib/docker` volumes, data ownership by UID 65532, configuration and certificates across restarts.
- PI-VERIFY-010: Backup and restore through the coordinator's documented commands, and an OS configuration backup (DietPi backup or a tar of `/boot/dietpi.txt`, `/etc`, the compose directory). Document the microSD re-image procedure.
- PI-VERIFY-011: `dmesg` and `journalctl -p warning -b`: no storage errors, OOM kills, Wi-Fi failures, undervoltage or throttling.
- PI-VERIFY-012: Headless administration from the desktop only; no keyboard or monitor used.
- PI-VERIFY-013: Optional passkeys on the user's Android phone (PK-012). This step needs the follow-up branch's passkey support on `main`; if it has not merged yet, record this step as blocked by it and continue. First verify the default: password sign-in on the phone at `https://<Pi LAN IP>:8443`, with the settings sentence explaining that passkeys need a trusted address. Then ask the user whether they want to try the optional Tailscale path (PK-001).
- PI-WEAR-001: Logs in RAM. Keep DietPi-RAMlog (`AUTO_SETUP_LOGGING_INDEX=-1`: `/var/log` on tmpfs, cleared hourly). Set journald to `Storage=volatile`, `RuntimeMaxUse=32M` in a drop-in, so the journal never reaches the card. Accept that system logs do not survive a reboot; the coordinator keeps its audit records in its own database.
- PI-WEAR-002: Container logs in RAM. Set Docker's default log driver to `journald` in `/etc/docker/daemon.json`, so container logs go to the volatile journal instead of `/var/lib/docker/containers/*/*.log` on the card. The repository's `compose.yaml` pins `json-file`; on the Pi, override it to `journald` with a `compose.override.yaml` next to it (or the repository's documented variable if the mission has made the driver configurable). `docker logs` and `docker compose logs` keep working with `journald`.
- PI-WEAR-003: No swap on the card. Set `AUTO_SETUP_SWAPFILE_LOCATION=zram` in `dietpi.txt` during FLASH-004 (verified key: `zram` puts swap on `/dev/zram0`, auto-size 50 percent of RAM) instead of the default 1.5 GB `/var/swap` file seen in the rehearsal. Confirm `swapon --show` lists only `/dev/zram0` and no file swap exists. This replaces the swap decision in SYS-003.
- PI-WEAR-004: Mount options. Root filesystem with `noatime` (check `/etc/fstab` and `findmnt -no OPTIONS /`; DietPi may already set it). `/tmp` on tmpfs (check). Leave the ext4 commit interval at its default unless the measurement in WEAR-009 shows a material gain; never above 60 s.
- PI-WEAR-005: TRIM. If the card supports discard (`lsblk -D` shows non-zero `DISC-GRAN`/`DISC-MAX`), enable the weekly `fstrim.timer`; do not mount with continuous `discard`. Keep at least a quarter of the card free, so the card's own wear levelling has spare blocks.
- PI-WEAR-006: APT. Store package indexes compressed (`Acquire::GzipIndexes "true"; Acquire::CompressionTypes::Order:: "gz";`), do not keep downloaded packages (`Binary::apt::APT::Keep-Downloaded-Packages "false"`), and autoclean after unattended upgrades. Updates themselves stay daily (section 7a); they are necessary writes.
- PI-WEAR-007: Health checks and timers. Docker records every health-check result in the container state on disk. Keep the coordinator's health check at an interval of at least 60 s on the Pi (override `healthcheck.interval` in `compose.override.yaml`) unless the repository documents a reason for less. Review `systemctl list-timers` and disable timers that write without value on this host (for example `man-db.timer`, and `e2scrub_all.timer` if present;
- PI-WEAR-008: Small periodic writers. `fake-hwclock` saves the time every hour so the clock is roughly right before network time arrives; keep it, but only if it is needed for a sane boot time without network (TLS and sessions depend on the clock), and otherwise reduce it to saving at shutdown. Disable anything else found by WEAR-009 that writes periodically without need.
- PI-WEAR-009: Measure, do not assume. Record bytes written to the card (`/sys/block/mmcblk0/stat`, field 7 is sectors written; multiply by 512) over 24 hours at idle with the coordinator running and no logins, before and after these changes. Identify every remaining writer (`fatrace -f W` for a few hours, or `/proc/<pid>/io` `write_bytes` per process) and classify each as necessary or removed.
- PI-WEAR-010: Plan for card failure anyway. Even with fewer writes the card will fail eventually. The coordinator backup (VERIFY-010) and the OS configuration backup are copied off the Pi to the desktop on a schedule (a desktop-side `systemd --user` timer pulling them over SSH daily is enough), and the re-image procedure in `BOOTSTRAP.md` must restore a working coordinator from those copies. Test the restore once.
