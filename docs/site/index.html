llm-usage

See every limit in one table.

Know before you start, not when it stops.

  • One table for every provider. Claude Code, Codex and Copilot, with their 5-hour, weekly and monthly limits, a bar for each and the time until it resets. Kilo, OpenCode, MiniMax and Z.ai show up when you use them.
  • A forecast, not only a number. The Guidance column compares your recent burn rate with the reset time, for example ! empty in 1h 20m. It appears after a few minutes of readings.
  • Fits your tooling. --json for scripts, --statusline for Claude Code, a live view with --watch, and an optional background sampler (--service-install) that keeps burn-rate history.
$ llm-usage --watch 60

ralph-robin

When one runs dry, the work moves on.

ralph-robin runs your prompt in a loop. Before every step it re-reads the limits and picks a provider that still has room. If every provider is blocked, it waits for the earliest reset. See the same hand-off inside a Bridge mission.

  • It chooses by headroom. By default it prefers the provider with the most room left against its weekly or monthly plan, so use is spread out and none runs dry first. You choose which providers are in the rotation (--providers claude,codex).
  • It never suspends without a wake alarm. If it cannot arm one, it waits with the machine awake. It also stops your desktop's idle timer from suspending the machine mid-run.
  • Test the wake path first. llm-sleep-soak suspends and wakes your machine repeatedly through the same code and reports late wakes and resume errors. It really suspends the machine.
  • Need a prompt to start exactly at a reset? llm-scheduler waits for the real reset time and then launches it.
$ ralph-robin --prompt-file task.md

LLM Bridge

Plan it. Run it. Review it.

For longer work, llm-bridge keeps missions. A mission is a goal and its task list, stored in a local database, so it survives a closed laptop, a dropped SSH session and a provider that hits its limit. You write the plan, the provider does the work in its own terminal, and nothing counts as done until you say so.

Watch the full 60-second run (scripted provider)

Write the goal once.

Add the follow-up tasks, with priorities and dependencies. Opening Bridge starts no provider. Keep several missions in different repositories and jump between them.

llm-bridge opens the home screenN creates a missionCtrl-] M picks another mission

The provider keeps its own terminal.

Claude Code, Codex or Copilot runs with its normal interface in a private tmux session. Paste, mouse and resize reach it. Bridge keeps one key, and the status line shows the way back.

Ctrl-] B Bridge controlsCtrl-] P back to the provider

A finished task waits for you.

When the provider exits cleanly, the task moves to VERIFYING and appears under Needs you. Approve it, or send it back with a reason; the reason goes into the next attempt's prompt. The next paid run waits until you decide. A verifier command that you configure can check the task first.

/approve accept/reject 2 needs tests send back/continue start the next task now

  • Many repositories, one picker. Ctrl-] M lists every mission, live ones first. Each mission has its own colour, and one detach returns you where you started.
  • Finish cleanly. /finish asks the provider to exit with its own command, so the task moves to review. Typing /exit in the provider does the same.
  • Change the rotation on the way. llm-bridge rotation --set claude,codex applies from the next provider selection. Out of capacity everywhere, the mission waits and says when.
  • Light, dark and plain. The theme follows your terminal; llm-bridge theme previews the others. NO_COLOR and ASCII under LANG=C work, and every state has a word as well as a colour.
  • Mouse wheel and paste. The wheel scrolls and selects in the controls. Inside the provider, paste, wheel and resize go to the provider.
  • People and scripts. Commands print readable text, and --json gives a stable machine-readable form. llm-bridge doctor checks tmux, storage and sign-ins offline and ends with your next step.

Built to be left alone

Leave it running. Stay in charge.

Agents that run unattended need a few guarantees. These are the ones llm-tools keeps.

Missions outlive your session.

Tasks, evidence and history live in a local SQLite database, and a native-mode provider runs in a private tmux session. A closed laptop, a dropped SSH session or a provider at its limit does not lose the plan. After a reboot, open the mission and type resume.

Nothing is accepted behind your back.

A clean exit is not a finished task. It waits for /approve, or you send it back with /reject and a reason. The next paid run holds until you decide. If you configure a verifier, Bridge records a hash of its files when the mission is created and does not run a changed one without your approval.

Know the burn before it happens.

The table forecasts when a limit will run out. ralph-robin spreads use across providers by remaining headroom, you choose the rotation, and when every provider is empty it sleeps until the earliest reset, never without a wake alarm.

No server, no account, no telemetry.

Plain Python and tmux in your terminal, over SSH as well as locally. It uses the sign-ins your provider CLIs already hold and opens no network listener. Apache-2.0. Each person runs their own copy; there is no shared server or dashboard.

Install

From install to your first approved task.

You need: Python 3.11+ and pipx; at least one provider CLI that is installed and signed in (claude, codex or copilot); tmux for Bridge. Linux is fully supported, macOS is best effort. Prefer scripts? The same flow runs without a terminal: see the README.

  1. 1Install

    pipx

    $ pipx install git+https://github.com/chrisgleissner/llm-tools.git@1.3.0

    From source

    $ git clone --branch 1.3.0 https://github.com/chrisgleissner/llm-tools.git$ cd llm-tools$ pipx install .

  2. 2Check your setup

    $ llm-bridge doctor

    It reads local files only and starts no provider. It checks tmux and your provider sign-ins, and its last line, Next, says what to fix or what to do next.

  3. 3Start a mission

    Use a folder you are happy for an agent to edit, such as a new empty git repository.

    $ cd your-project$ llm-bridge

    Press N and type the task, for example Create a file named hello.txt containing the word hello, then stop. The form selects the first provider that is installed and signed in. Press Tab five times to reach Start and open provider, then Enter. This starts the provider and uses its capacity.

    Claude Code first asks whether you trust the folder. Choose Yes, I trust this folder. The first option is No, exit: if you pick it, Claude exits and Bridge starts it again about a minute later, so you can choose Yes.

  4. 4Finish and approve

    When the provider says it is done, exit it with its own command (/exit in Claude Code). Or press Ctrl-] then B and type /finish, and Bridge does it for you. Bridge then reports that task 1 is waiting for your review.

    In the controls (Ctrl-] B), type /approve, press Enter, then y to confirm. The task shows COMPLETED and hello.txt is in your folder. Leave with Ctrl-] D, then Ctrl-D.

How long it takes. In the recorded walk-through with Claude Code, pipx install took 13 seconds and llm-bridge doctor 0.1 seconds. From Start to a completed task took 31 seconds, about half of it spent typing and choosing. Your provider's own speed will differ.

Optional: see all your limits. Run llm-usage. It reads every installed provider at once. On the machine we measured, the first table appeared after about 3 seconds and slower providers filled in by 9 seconds. An installed background sampler makes later runs quick.

Other install routes are in the reference, settings in configuration, and details in the Bridge operations guide.

Know the limits

What it does, and what it does not.

It drives CLIs you already have.

It is not a provider and not a proxy. It uses the sign-ins your provider CLIs already hold. Bridge starts each provider without the other providers' credential variables, but it does not sandbox a provider: providers run as you, in your project folder.

Linux first, macOS best effort.

Suspend and wake use systemd, so they are Linux only. Elsewhere the tools wait with the machine awake. Continuous integration runs on Linux.

Resume is exact for Codex only.

Exact session resume is verified for Codex. Claude Code and Copilot continue from rebuilt context. Providers run as you, so read the diff before you approve.

Numbers can break.

Usage endpoints are rate limited, and providers change their formats without notice. A figure that cannot be read shows as unavailable with a reason, never as a guess. After an HTTP 429 from Claude, readers share a cool-down of at least 60 seconds.

Privacy: what it reads, calls and writes

Reads from disk
Claude Code's ~/.claude/.credentials.json (to call the usage endpoint) and its project files under ~/.claude/projects as a fallback. Codex's ~/.codex/auth.json (checked for sign-in) and session files under ~/.codex/sessions. For Copilot, a GitHub token from COPILOT_GITHUB_TOKEN, GH_TOKEN, GITHUB_TOKEN or gh auth token. If you configure z.ai, its key from Kilo's or OpenCode's auth file.
Calls
api.anthropic.com for Claude usage and token refresh. api.github.com for Copilot quota and billing. Codex is queried through the Codex CLI itself (codex app-server). The z.ai quota endpoint, only if you use z.ai. Nothing is sent to any server of ours: there is none.
Writes
Caches and logs under ~/.cache/llm-tools and Bridge's database under ~/.local/state/llm-tools. One change outside them: before reading Copilot's footer it enables two status-line items in ~/.copilot/settings.json. Set LLM_USAGE_COPILOT_NO_SETTINGS_WRITE=1 to prevent that.
Never
No telemetry and no network listener. The optional usage sampler listens on a Unix socket owned by you; Bridge uses a local SQLite file and a private tmux socket. This page loads no scripts, fonts or analytics from other hosts; the badges at the bottom are images from GitHub and shields.io.

FAQ

Questions engineers ask first.

How is this different from usage readers or agent session managers?

By capability, llm-tools does three things together. It reads the quota that remains, with a reset time and a forecast, rather than only the tokens you spent. It acts on that: it moves a prompt to another provider or waits for the reset. And for longer work, it keeps a task list with explicit approval in a local database while each provider keeps its own terminal.

If you need only one of these, a smaller tool may fit you better. Each part works on its own: you can use llm-usage and nothing else.

What does it read from disk?

Provider sign-in and session files, to find a token or a number: Claude Code's credentials and project files, Codex's auth.json and session files, and a GitHub token for Copilot. The full list, with what it calls and writes, is under Privacy. llm-bridge doctor checks sign-in files by reading local files only; it sends no request.

Will quota reads get my account flagged?

It reads your own quota, with your own sign-in, from the quota endpoints that the provider CLIs use for the same information. It keeps the rate low: Claude readings are shared for up to 60 seconds, retries are bounded, and a 429 response starts a cool-down. Provider terms are the provider's to define and they can change, so read yours. To stop reading a provider, remove it from [usage].providers in the config.

What happens when a provider changes its output?

The affected row shows unavailable with a reason, for example not-authenticated or rate-limited, and the other providers keep working. ralph-robin does not treat an unreadable limit as proof of capacity: it waits a bounded time (15 minutes by default) and then tries that provider anyway, so one broken reader cannot stall a run. The fix is a new release.

Which providers work?

Claude Code, Codex and Copilot CLI are first-class: llm-usage reads them and Bridge supervises them. Kilo Code and OpenCode work as configured routes (a named pairing of a CLI and a model), which is also how z.ai models are launched. MiniMax works only for runs without a terminal session. You do not need every CLI: a missing provider shows as unavailable and the rest keep working.

Will ralph-robin suspend my computer?

Only when every provider in the rotation is blocked, and never without an armed wake alarm. It checks how far each wake lands from its target and falls back to waiting awake if it cannot arm one. Run llm-sleep-soak first to test your hardware.

Does it spend my capacity on its own?

No. llm-usage only reads. Opening llm-bridge starts no provider; capacity is used when you choose Start and open provider, run llm-bridge start, or launch ralph-robin or llm-scheduler.

Is it for teams?

It is a per-user tool. Missions, caches and sign-ins belong to your account, and there is no shared server or dashboard. It runs on a remote machine over SSH, and Apache-2.0 allows internal use. Each person needs their own provider sign-ins.

Is this an official billing dashboard?

No. It uses local data and locally signed-in CLIs, and provider formats can change. Missing or inconclusive data is shown as unavailable rather than guessed.
